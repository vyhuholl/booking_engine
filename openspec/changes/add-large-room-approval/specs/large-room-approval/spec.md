## ADDED Requirements

### Requirement: Создание брони большой комнаты требует одобрения
Система SHALL при `POST /bookings` определять размер комнаты по её `capacity`. Если
`capacity > 12`, бронь MUST создаваться в статусе `pending_approval`, а ответ MUST быть
HTTP **202 Accepted** (а не 201). Для комнат с `capacity ≤ 12` поведение не меняется:
бронь создаётся в статусе `confirmed` с ответом HTTP 201. Все прочие проверки создания
(валидация интервала, длительность, существование комнаты, `out_of_service`, пересечение
с занятыми слотами) применяются одинаково к обоим случаям.

#### Scenario: Бронь большой комнаты создаётся на согласовании
- **WHEN** аутентифицированный пользователь выполняет `POST /bookings` на свободный
  интервал комнаты с `capacity = 20`
- **THEN** система возвращает HTTP 202 с созданной бронью в статусе `pending_approval`
- **AND** бронь содержит поля `id`, `room_id`, `user_id`, `title`, `start_time`,
  `end_time`, `status`

#### Scenario: Бронь малой комнаты подтверждается сразу
- **WHEN** пользователь выполняет `POST /bookings` на свободный интервал комнаты с
  `capacity = 12`
- **THEN** система возвращает HTTP 201 с бронью в статусе `confirmed`

#### Scenario: Порог по вместимости — строго больше 12
- **WHEN** пользователь бронирует комнату с `capacity = 13`
- **THEN** система возвращает HTTP 202 и статус `pending_approval`

#### Scenario: Валидация применяется и к большим комнатам
- **WHEN** пользователь бронирует комнату с `capacity = 20` на интервал с длительностью
  меньше 15 минут
- **THEN** система возвращает HTTP 400 с кодом `BOOKING_DURATION_TOO_SHORT`
- **AND** бронь не создаётся

### Requirement: Слот с pending_approval бронью считается занятым
Система MUST считать интервал комнаты занятым, если на него есть бронь в статусе
`confirmed`, `pending_approval` **или** `approved`. Пока бронь ожидает одобрения или
одобрена, другой пользователь не MUST иметь возможности забронировать пересекающийся
слот. Отклонённые (`rejected`) и отменённые (`cancelled`) брони MUST освобождать слот и
не учитываться в проверке пересечений.

#### Scenario: Нельзя забронировать слот, удерживаемый pending_approval бронью
- **WHEN** на интервал `[10:00, 11:00)` большой комнаты есть бронь в статусе
  `pending_approval`, и другой пользователь выполняет `POST /bookings` на
  пересекающийся интервал
- **THEN** система возвращает HTTP 409 с кодом `BOOKING_CONFLICT`

#### Scenario: Одобренная бронь продолжает удерживать слот
- **WHEN** бронь на интервал `[10:00, 11:00)` переведена в `approved`, и другой
  пользователь бронирует пересекающийся интервал
- **THEN** система возвращает HTTP 409 с кодом `BOOKING_CONFLICT`

#### Scenario: Отклонённая бронь освобождает слот
- **WHEN** бронь на интервал `[10:00, 11:00)` переведена в `rejected`, и другой
  пользователь бронирует тот же интервал
- **THEN** система создаёт бронь (HTTP 201 или 202 в зависимости от размера комнаты)

### Requirement: Просмотр броней, ожидающих одобрения
Система SHALL возвращать список броней в статусе `pending_approval` запросом
`GET /admin/approvals`. Эндпоинт MUST быть доступен только пользователю с ролью `admin`;
любой другой роли система MUST отказать. Перед возвратом список MUST быть очищен от
броней, у которых истёк 24-часовой таймаут одобрения (они авто-отклоняются, см.
требование о таймауте) и в ответ не попадают.

#### Scenario: Admin видит ожидающие одобрения брони
- **WHEN** admin выполняет `GET /admin/approvals` при наличии двух броней в статусе
  `pending_approval`
- **THEN** система возвращает HTTP 200 с JSON-массивом этих двух броней
- **AND** каждая бронь содержит `id`, `room_id`, `user_id`, `title`, `start_time`,
  `end_time`, `status`

#### Scenario: Пустой список ожидающих
- **WHEN** нет броней в статусе `pending_approval`
- **THEN** система возвращает HTTP 200 с пустым массивом `[]`

#### Scenario: Не-admin не имеет доступа к списку
- **WHEN** пользователь с ролью `member` или `manager` выполняет `GET /admin/approvals`
- **THEN** система возвращает HTTP 403 с кодом `FORBIDDEN`

#### Scenario: Требование аутентификации
- **WHEN** запрос выполнен без валидного JWT
- **THEN** система возвращает HTTP 401

### Requirement: Одобрение брони администратором
Система SHALL позволять пользователю с ролью `admin` одобрить бронь запросом
`POST /admin/approvals/{id}/approve`. При одобрении бронь в статусе `pending_approval`
MUST переводиться в статус `approved` и становиться активной. Одобрять MUST только
`admin`. Одобрение брони не в статусе `pending_approval` (уже `approved`, `rejected` или
`cancelled`) MUST отклоняться как ошибка идемпотентности.

#### Scenario: Успешное одобрение
- **WHEN** admin выполняет `POST /admin/approvals/{id}/approve` для брони в статусе
  `pending_approval`
- **THEN** система возвращает HTTP 200 с бронью в статусе `approved`

#### Scenario: Одобрение не-админом запрещено
- **WHEN** пользователь с ролью `member` или `manager` вызывает approve
- **THEN** система возвращает HTTP 403 с кодом `FORBIDDEN`
- **AND** статус брони не меняется

#### Scenario: Повторное одобрение — ошибка
- **WHEN** admin одобряет бронь, уже находящуюся в статусе `approved`
- **THEN** система возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

#### Scenario: Одобрение несуществующей брони
- **WHEN** admin вызывает approve для несуществующего `id`
- **THEN** система возвращает HTTP 404 с кодом `APPROVAL_NOT_FOUND`

### Requirement: Отклонение брони с причиной
Система SHALL позволять пользователю с ролью `admin` отклонить бронь запросом
`POST /admin/approvals/{id}/reject` с телом `{ "reason": "<текст>" }`. При отклонении
бронь в статусе `pending_approval` MUST переводиться в статус `rejected`, удерживаемый
слот MUST освобождаться (перестаёт учитываться в проверке пересечений), а причина отказа
MUST сохраняться в брони. Причина (`reason`) MUST быть непустой строкой. Отклонять MUST
только `admin`. Отклонение брони не в статусе `pending_approval` MUST отклоняться как
ошибка идемпотентности. Освободившийся слот MUST в **той же транзакции** предлагаться листу
ожидания так же, как при отмене брони: первой подходящей `waiting`-записи (по возрастанию
`position`) на пересекающийся интервал (см. `booking-waitlist` → «Предложение слота при
отмене брони»). Отклонение MUST завершаться успешно даже если подходящей записи нет.

#### Scenario: Успешное отклонение с причиной
- **WHEN** admin выполняет `POST /admin/approvals/{id}/reject` с телом
  `{ "reason": "комната зарезервирована под мероприятие" }` для брони в статусе
  `pending_approval`
- **THEN** система возвращает HTTP 200 с бронью в статусе `rejected`
- **AND** причина отказа сохранена и возвращается в поле `rejection_reason`
- **AND** слот освобождается: другой пользователь может забронировать тот же интервал

#### Scenario: Отклонение предлагает освободившийся слот листу ожидания
- **WHEN** admin отклоняет `pending_approval`-бронь на `[10:00, 11:00)`, а в очереди есть
  `waiting`-запись на пересекающийся интервал с позицией 1
- **THEN** система возвращает HTTP 200 с бронью в статусе `rejected`
- **AND** запись с позицией 1 в той же транзакции переводится в статус `offered` с
  зафиксированным временем предложения

#### Scenario: Отклонение без очереди на слот
- **WHEN** admin отклоняет `pending_approval`-бронь, но нет `waiting`-записей на
  пересекающийся интервал
- **THEN** отклонение проходит успешно (HTTP 200) и ни одна запись не переводится в `offered`

#### Scenario: Отклонение без причины запрещено
- **WHEN** admin вызывает reject с пустым или отсутствующим `reason`
- **THEN** система возвращает HTTP 400 с кодом `VALIDATION_ERROR`
- **AND** статус брони не меняется

#### Scenario: Отклонение не-админом запрещено
- **WHEN** пользователь с ролью `member` или `manager` вызывает reject
- **THEN** система возвращает HTTP 403 с кодом `FORBIDDEN`

#### Scenario: Повторное отклонение — ошибка
- **WHEN** admin отклоняет бронь, уже находящуюся в статусе `rejected` или `approved`
- **THEN** система возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

#### Scenario: Отклонение несуществующей брони
- **WHEN** admin вызывает reject для несуществующего `id`
- **THEN** система возвращает HTTP 404 с кодом `APPROVAL_NOT_FOUND`

### Requirement: Автоматический таймаут одобрения
Система MUST автоматически отклонять бронь, если она пробыла в статусе
`pending_approval` дольше 24 часов с момента создания и admin не принял решение.
Таймаут MUST проверяться лениво — при обращении к брони (в списке `GET /admin/approvals`,
при `approve` или `reject`), без фонового cron-воркера. При срабатывании таймаута бронь
MUST переводиться в статус `rejected` с причиной, обозначающей автоматическое отклонение
по таймауту, а слот MUST освобождаться и, как при обычном отклонении, предлагаться листу
ожидания (первой подходящей `waiting`-записи). Попытка одобрить или отклонить бронь с
истёкшим таймаутом MUST завершаться ошибкой (бронь уже не в статусе `pending_approval`).

#### Scenario: Просроченная бронь авто-отклоняется и не попадает в список
- **WHEN** бронь пробыла в статусе `pending_approval` более 24 часов и admin выполняет
  `GET /admin/approvals`
- **THEN** эта бронь переводится в статус `rejected` с причиной авто-отклонения
- **AND** она не входит в возвращённый список ожидающих

#### Scenario: Одобрение просроченной брони невозможно
- **WHEN** admin вызывает approve для брони, пробывшей в `pending_approval` более 24 часов
- **THEN** бронь считается авто-отклонённой (`rejected`)
- **AND** система возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

#### Scenario: Бронь в пределах таймаута одобряется штатно
- **WHEN** с момента создания `pending_approval` брони прошло менее 24 часов и admin
  вызывает approve
- **THEN** бронь переводится в статус `approved`

### Requirement: Идемпотентность и конкурентная безопасность смены статуса
Система MUST гарантировать, что смена статуса `pending_approval` → `approved`/`rejected`
атомарна и однократна. При двух одновременных запросах на одобрение одной брони ровно
один запрос MUST завершиться успехом, а второй — получить ошибку и не менять уже
установленный статус. Одобрение и отклонение MUST быть взаимоисключающими: если бронь уже
одобрена, отклонить её нельзя, и наоборот.

#### Scenario: Гонка двух одобрений
- **WHEN** два admin-запроса `approve` на одну `pending_approval`-бронь выполняются
  одновременно
- **THEN** ровно один возвращает HTTP 200 с бронью в статусе `approved`
- **AND** второй возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

#### Scenario: Одобрение и отклонение конкурируют
- **WHEN** одновременно выполняются `approve` и `reject` одной `pending_approval`-брони
- **THEN** успешным становится ровно один из них
- **AND** второй возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

### Requirement: Приоритет отмены пользователем над одобрением
Система MUST позволять владельцу (или admin/менеджеру по общим правилам отмены) отменить
бронь в статусе `pending_approval` — отмена имеет приоритет над одобрением. После отмены
бронь переходит в `cancelled`, слот освобождается, и последующее одобрение или отклонение
этой брони MUST завершаться ошибкой (бронь уже не в статусе `pending_approval`).

#### Scenario: Отмена pending_approval брони владельцем
- **WHEN** владелец отменяет свою бронь в статусе `pending_approval` в пределах дедлайна
  отмены
- **THEN** система возвращает HTTP 200 с бронью в статусе `cancelled`
- **AND** слот освобождается

#### Scenario: Одобрение отменённой брони невозможно
- **WHEN** бронь была отменена пользователем, и затем admin вызывает approve
- **THEN** система возвращает HTTP 409 с кодом `NOT_PENDING_APPROVAL`

### Requirement: Публикация событий смены статуса
Система MUST публиковать доменное событие в Kafka при каждой смене статуса брони в рамках
workflow одобрения: `booking.pending_approval` при создании брони на согласование,
`booking.approved` при одобрении, `booking.rejected` при отклонении (включая
авто-отклонение по таймауту). Сбой публикации MUST быть деградацией, а не провалом
операции: бронь уже зафиксирована в БД, поэтому событие не откатывает изменение
(eventual consistency, как для существующих событий брони).

#### Scenario: Событие при создании на согласование
- **WHEN** создаётся бронь большой комнаты в статусе `pending_approval`
- **THEN** в Kafka публикуется событие типа `booking.pending_approval` с
  идентификаторами брони, пользователя и комнаты

#### Scenario: Событие при одобрении
- **WHEN** admin одобряет бронь
- **THEN** в Kafka публикуется событие типа `booking.approved`

#### Scenario: Событие при отклонении
- **WHEN** бронь отклоняется админом или авто-отклоняется по таймауту
- **THEN** в Kafka публикуется событие типа `booking.rejected`

#### Scenario: Сбой публикации не откатывает смену статуса
- **WHEN** смена статуса зафиксирована в БД, но публикация в Kafka не удалась
- **THEN** операция считается успешной (статус изменён), сбой публикации логируется на
  уровне Warn
