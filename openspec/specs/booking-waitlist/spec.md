## Requirements
### Requirement: Постановка в очередь на занятый интервал
Система SHALL позволять аутентифицированному пользователю встать в лист ожидания на интервал
комнаты запросом `POST /rooms/{id}/waitlist` с телом `{ "start_time", "end_time" }`.
Waitlist-запись MUST создаваться **только если** комната занята (есть подтверждённая бронь,
пересекающая запрошенный интервал). Если комната свободна в этом интервале, система MUST отказать
и указать, что нужно оформить обычную бронь. Интервал MUST проходить те же проверки, что и обычная
бронь: `end_time > start_time`, `start_time` в будущем, длительность в диапазоне
`[15 минут, 8 часов]`. Комната MUST существовать и не быть `out_of_service`.

#### Scenario: Успешная постановка в очередь на занятый интервал
- **WHEN** комната занята подтверждённой бронью в интервале `[10:00, 11:00)` и member выполняет `POST /rooms/{id}/waitlist` с `start_time=10:00`, `end_time=11:00`
- **THEN** система возвращает HTTP 201 с waitlist-записью в статусе `waiting`
- **AND** запись содержит поля `id`, `room_id`, `user_id`, `start_time`, `end_time`, `position`, `status`
- **AND** `position` назначен автоматически (следующий свободный номер в очереди комнаты)

#### Scenario: Отказ, если комната свободна в интервале
- **WHEN** в запрошенном интервале нет подтверждённых броней
- **THEN** система возвращает HTTP 409 с кодом `WAITLIST_ROOM_AVAILABLE`
- **AND** waitlist-запись не создаётся

#### Scenario: Отказ при невалидном интервале
- **WHEN** пользователь передаёт `end_time <= start_time`, либо `start_time` в прошлом, либо длительность вне диапазона `[15 минут, 8 часов]`
- **THEN** система возвращает HTTP 400 с соответствующим кодом валидации (`INVALID_TIME_RANGE` / `START_IN_PAST` / `BOOKING_DURATION_TOO_SHORT` / `BOOKING_DURATION_TOO_LONG`)

#### Scenario: Отказ для несуществующей комнаты
- **WHEN** пользователь ставит в очередь на несуществующую комнату
- **THEN** система возвращает HTTP 404 с кодом `ROOM_NOT_FOUND`

#### Scenario: Отказ для комнаты вне обслуживания
- **WHEN** комната имеет статус `out_of_service`
- **THEN** система возвращает HTTP 409 с кодом `ROOM_OUT_OF_SERVICE`

#### Scenario: Требование аутентификации
- **WHEN** запрос выполнен без валидного JWT
- **THEN** система возвращает HTTP 401

### Requirement: Уникальность записи пользователя в очереди
Система MUST гарантировать инвариант: один пользователь может иметь не более одной активной
(`waiting` или `offered`) waitlist-записи на конкретный интервал конкретной комнаты. Повторная
постановка в очередь на тот же интервал той же комнаты MUST отклоняться.

#### Scenario: Повторная постановка в ту же очередь запрещена
- **WHEN** пользователь уже имеет `waiting`-запись на интервал `[10:00, 11:00)` комнаты и снова выполняет `POST /rooms/{id}/waitlist` на тот же интервал
- **THEN** система возвращает HTTP 409 с кодом `ALREADY_IN_WAITLIST`
- **AND** дубликат не создаётся

#### Scenario: Разные интервалы одной комнаты допустимы
- **WHEN** пользователь имеет запись на интервал `[10:00, 11:00)` и ставит запись на `[12:00, 13:00)` той же комнаты (оба заняты)
- **THEN** система возвращает HTTP 201 и создаёт вторую запись

### Requirement: Автоматическое назначение позиции в очереди
Система MUST назначать `position` автоматически при создании записи как следующий порядковый
номер в очереди комнаты; клиент не MUST иметь возможности задать или изменить `position`.
Позиция отражает порядок постановки в очередь и используется при выборе следующей записи для
предложения слота.

#### Scenario: Позиции возрастают по порядку постановки
- **WHEN** три пользователя последовательно встают в очередь одной комнаты на пересекающиеся интервалы
- **THEN** их записи получают возрастающие значения `position` в порядке постановки

#### Scenario: Переданный клиентом position игнорируется
- **WHEN** тело запроса содержит поле `position`
- **THEN** система игнорирует его и назначает позицию автоматически

### Requirement: Просмотр очереди комнаты
Система SHALL возвращать очередь комнаты запросом `GET /rooms/{id}/waitlist` — список
waitlist-записей комнаты с их `position` и `status`, отсортированный по `position` по возрастанию.

#### Scenario: Успешный просмотр очереди
- **WHEN** аутентифицированный пользователь выполняет `GET /rooms/{id}/waitlist`
- **THEN** система возвращает HTTP 200 с JSON-массивом записей, отсортированным по `position` ASC
- **AND** каждая запись содержит `id`, `user_id`, `start_time`, `end_time`, `position`, `status`

#### Scenario: Пустая очередь
- **WHEN** у комнаты нет waitlist-записей
- **THEN** система возвращает HTTP 200 с пустым массивом `[]`

### Requirement: Предложение слота при отмене брони
При отмене подтверждённой брони система MUST в **одной транзакции** с отменой найти первую
(по возрастанию `position`) waitlist-запись в статусе `waiting`, чей интервал пересекается с
интервалом отменённой брони, и перевести её в статус `offered`, зафиксировав время предложения.
Отмена брони MUST завершаться успешно даже если подходящей waitlist-записи нет. Предложение слота
MUST быть атомарным: одна и та же запись не MUST быть предложена двум операциям одновременно.

#### Scenario: Отмена предлагает слот первому в очереди
- **WHEN** бронь на `[10:00, 11:00)` отменяется, а в очереди есть `waiting`-записи на пересекающиеся интервалы с позициями 1 и 2
- **THEN** отмена проходит успешно (HTTP 200)
- **AND** запись с позицией 1 переводится в статус `offered` с зафиксированным временем предложения
- **AND** запись с позицией 2 остаётся в статусе `waiting`

#### Scenario: Отмена без подходящей очереди
- **WHEN** бронь отменяется, но нет `waiting`-записей на пересекающийся интервал
- **THEN** отмена проходит успешно (HTTP 200) и ни одна запись не переводится в `offered`

#### Scenario: Отмена и предложение атомарны
- **WHEN** отмена брони не может быть зафиксирована в БД (транзакция откатывается)
- **THEN** ни статус брони, ни статус waitlist-записи не изменяются

### Requirement: Подтверждение предложенного слота
Система SHALL позволять владельцу `offered`-записи подтвердить слот запросом
`POST /waitlist/{id}/confirm`. При подтверждении в пределах таймаута система MUST в одной
транзакции создать обычную подтверждённую бронь на интервал записи и перевести запись в статус
`converted`. Подтверждать MUST только владелец записи. Подтверждение записи не в статусе `offered`
MUST отклоняться.

#### Scenario: Успешное подтверждение слота
- **WHEN** владелец `offered`-записи выполняет `POST /waitlist/{id}/confirm` в пределах 15 минут с момента предложения
- **THEN** система возвращает HTTP 201 с созданной бронью в статусе `confirmed`
- **AND** waitlist-запись переводится в статус `converted`

#### Scenario: Подтверждение чужой записи запрещено
- **WHEN** пользователь пытается подтвердить `offered`-запись, принадлежащую другому пользователю
- **THEN** система возвращает HTTP 403 с кодом `WAITLIST_FORBIDDEN`

#### Scenario: Подтверждение записи не в статусе offered
- **WHEN** пользователь подтверждает запись в статусе `waiting`, `expired` или `converted`
- **THEN** система возвращает HTTP 409 с кодом `OFFER_NOT_PENDING`

#### Scenario: Подтверждение несуществующей записи
- **WHEN** пользователь подтверждает несуществующий `id`
- **THEN** система возвращает HTTP 404 с кодом `WAITLIST_NOT_FOUND`

### Requirement: Таймаут предложенного слота
Предложенный слот MUST быть подтверждён в течение 15 минут с момента предложения. Протухание
проверяется лениво при `confirm` (фоновый воркер не используется). Если с момента предложения
прошло больше 15 минут, система MUST перевести запись в статус `expired`, предложить слот
следующей подходящей `waiting`-записи (по возрастанию `position`) в той же транзакции и отклонить
подтверждение.

#### Scenario: Подтверждение после таймаута
- **WHEN** владелец `offered`-записи выполняет `confirm` спустя более 15 минут после предложения
- **THEN** система возвращает HTTP 409 с кодом `OFFER_EXPIRED`
- **AND** запись переводится в статус `expired`
- **AND** бронь не создаётся

#### Scenario: Протухший слот предлагается следующему
- **WHEN** `offered`-запись протухает при `confirm`, а в очереди есть следующая `waiting`-запись на пересекающийся интервал
- **THEN** следующая запись (по наименьшему `position`) переводится в статус `offered`

#### Scenario: Протухание без следующего кандидата
- **WHEN** `offered`-запись протухает, а других `waiting`-записей на пересекающийся интервал нет
- **THEN** запись переводится в `expired` и ни одна запись не переводится в `offered`

### Requirement: Атомарность конкурентного подтверждения
Система MUST гарантировать, что при двух одновременных запросах на подтверждение одной
`offered`-записи ровно один запрос завершается успехом (создаёт бронь, переводит запись в
`converted`), а второй получает ошибку и не создаёт дублирующую бронь.

#### Scenario: Гонка двух подтверждений одного слота
- **WHEN** два запроса `confirm` на одну `offered`-запись выполняются одновременно
- **THEN** ровно один возвращает HTTP 201 с созданной бронью
- **AND** второй возвращает ошибку (`OFFER_NOT_PENDING` или конфликт брони) и в БД остаётся ровно одна бронь на интервал

### Requirement: Выход из очереди
Система SHALL позволять владельцу waitlist-записи выйти из очереди запросом
`DELETE /waitlist/{id}`. Удалять MUST только владелец записи (либо admin).

#### Scenario: Успешный выход из очереди
- **WHEN** владелец записи выполняет `DELETE /waitlist/{id}`
- **THEN** система возвращает HTTP 204 и запись удаляется из очереди

#### Scenario: Выход из чужой записи запрещён
- **WHEN** пользователь пытается удалить запись другого пользователя
- **THEN** система возвращает HTTP 403 с кодом `WAITLIST_FORBIDDEN`

#### Scenario: Выход из несуществующей записи
- **WHEN** пользователь удаляет несуществующий `id`
- **THEN** система возвращает HTTP 404 с кодом `WAITLIST_NOT_FOUND`
