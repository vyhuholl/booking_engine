## Requirements
### Requirement: Отдельный процесс-потребитель событий бронирования
Система SHALL предоставлять отдельный процесс `cmd/notifier`, который потребляет доменные
события бронирования из Kafka-топика `booking-events` как участник consumer-group. Процесс
MUST запускаться независимо от HTTP-сервера и не MUST быть частью его жизненного цикла.
Процесс MUST завершаться gracefully по `SIGINT`/`SIGTERM`: прекращать чтение новых сообщений,
дожидаться завершения обработки текущего события и закрывать соединения (Kafka, БД).
Конфигурация MUST браться из окружения (`DATABASE_URL`, `KAFKA_BROKERS`, `KAFKA_TOPIC`,
`KAFKA_GROUP_ID`, параметры retry/backoff).

#### Scenario: Потребление события из топика
- **WHEN** в топик `booking-events` опубликовано событие бронирования
- **THEN** процесс-нотификатор вычитывает его как участник consumer-group
- **AND** trace-контекст восстанавливается из заголовков сообщения (`traceparent`), чтобы трейс продюсера продолжился в нотификаторе

#### Scenario: Graceful shutdown
- **WHEN** процесс получает `SIGTERM` во время обработки события
- **THEN** он завершает обработку текущего события, коммитит его offset и закрывает Kafka- и БД-соединения перед выходом
- **AND** не начинает обработку новых сообщений

#### Scenario: Независимость от HTTP-сервера
- **WHEN** HTTP-сервер остановлен или недоступен
- **THEN** процесс-нотификатор продолжает потреблять события и рассылать уведомления

### Requirement: Маппинг типов событий на адресатов уведомлений
Система SHALL для каждого типа события определять адресатов и содержание уведомления:
- `booking.created` → владелец брони (`user_id`), тип `booking_confirmed`.
- `booking.cancelled` → владелец брони (`user_id`), тип `booking_cancelled`.
- `booking.pending_approval` → **все** пользователи с ролью `admin`, тип `approval_requested`.
- `booking.approved` → создатель брони (`user_id`), тип `booking_approved`.
- `booking.rejected` → создатель брони (`user_id`), тип `booking_rejected`, с причиной отказа.
Список админов MUST определяться на момент обработки события (чтение из хранилища
пользователей). Причина отказа для `booking.rejected` и детали брони (комната, интервал)
MUST обогащаться из хранилища броней, так как тело события несёт только идентификаторы.
Событие неизвестного/необрабатываемого типа MUST игнорироваться без ошибки (offset
коммитится), с записью в лог на уровне `Info`.

#### Scenario: Уведомление владельца о создании брони
- **WHEN** получено событие `booking.created` с `user_id = U`
- **THEN** система отправляет пользователю `U` уведомление типа `booking_confirmed`

#### Scenario: Уведомление всех админов о запросе на согласование
- **WHEN** получено событие `booking.pending_approval` и в системе есть админы `A1`, `A2`
- **THEN** система отправляет уведомление типа `approval_requested` каждому из `A1` и `A2`

#### Scenario: Уведомление об отклонении несёт причину
- **WHEN** получено событие `booking.rejected` для брони с сохранённой причиной отказа
- **THEN** система отправляет создателю брони уведомление типа `booking_rejected`, содержащее причину отказа

#### Scenario: Игнорирование неизвестного типа события
- **WHEN** получено событие с неизвестным `type`
- **THEN** уведомления не отправляются, событие логируется на уровне `Info`, offset коммитится

### Requirement: Интерфейс доставки Notifier и заглушка LogNotifier
Система SHALL определять интерфейс доставки
`Notifier.Send(ctx context.Context, userID uuid.UUID, n Notification) error`.
Логика потребления MUST зависеть только от этого интерфейса, а не от конкретной реализации.
Система MUST предоставлять реализацию-заглушку `LogNotifier`, которая пишет уведомление в
структурный лог (`log/slog`) и никогда не логирует PII/секреты. Реализация выбирается при
wiring процесса.

#### Scenario: LogNotifier пишет уведомление в лог
- **WHEN** `LogNotifier.Send` вызван с `userID` и уведомлением
- **THEN** уведомление записывается через `slog` с полями `user_id`, `type`, `booking_id` и возвращается `nil`
- **AND** в лог не попадают токены, пароли и полные тела запросов

#### Scenario: Обработка не зависит от реализации Notifier
- **WHEN** процесс сконфигурирован с другой реализацией `Notifier`
- **THEN** диспетчер событий работает без изменений, вызывая только `Send`

### Requirement: Идемпотентная обработка (дедупликация по event ID)
Система SHALL обрабатывать каждое событие идемпотентно: повторная обработка события с тем же
`event_id` MUST NOT приводить к повторной отправке уведомлений. Идентификатор обработанного
события MUST сохраняться в устойчивом хранилище (таблица `processed_events`). Перед отправкой
уведомлений система MUST проверять, не обработан ли `event_id` ранее; после успешной обработки
MUST фиксировать `event_id` как обработанный. Дедупликация ведётся на уровне события (одно
событие может породить несколько уведомлений — например всем админам).

#### Scenario: Повторная доставка того же события не дублирует уведомления
- **WHEN** событие с `event_id = E` уже было полностью обработано, и Kafka повторно доставляет его
- **THEN** система распознаёт `E` как обработанный и не отправляет уведомления повторно
- **AND** offset коммитится

#### Scenario: Первичная обработка фиксирует event ID
- **WHEN** событие с новым `event_id = E` успешно обработано
- **THEN** `E` сохраняется в `processed_events`

### Requirement: Гарантия доставки at-least-once
Система SHALL гарантировать доставку уведомлений «хотя бы один раз»: offset события MUST
коммититься только после завершения его обработки (успешной отправки или отправки в
dead-letter). Потеря события (коммит offset до обработки) MUST NOT происходить. Дубликаты
уведомлений при этом допустимы.

#### Scenario: Событие не теряется при падении до обработки
- **WHEN** процесс падает после чтения события, но до завершения его обработки
- **THEN** после перезапуска событие вычитывается снова (offset не был закоммичен) и обрабатывается
- **AND** дедупликация по `event_id` предотвращает повтор, если предыдущая обработка успела зафиксировать `event_id`

### Requirement: Retry с backoff и dead-letter при ошибке доставки
Система SHALL при ошибке `Notifier.Send` повторять отправку с экспоненциальной задержкой
(backoff) до `N` попыток (конфигурируемо). Если все `N` попыток исчерпаны, событие (или
конкретное недоставленное уведомление) MUST помещаться в dead-letter (таблица
`notification_dead_letter`) с сохранением `event_id`, адресата, типа и причины последней
ошибки; после этого обработка события MUST считаться завершённой (offset коммитится), чтобы
одно «отравленное» сообщение не блокировало очередь.

#### Scenario: Успех после повторной попытки
- **WHEN** первая попытка `Send` возвращает ошибку, а вторая — успех
- **THEN** уведомление считается доставленным, dead-letter не используется

#### Scenario: Dead-letter после исчерпания попыток
- **WHEN** все `N` попыток `Send` завершились ошибкой
- **THEN** запись помещается в `notification_dead_letter` с `event_id`, адресатом и причиной ошибки
- **AND** offset события коммитится, обработка следующих событий продолжается

### Requirement: Контракт события несёт стабильный идентификатор
Система SHALL гарантировать, что каждое публикуемое доменное событие бронирования несёт поле
`event_id` (формат `evt-<uuid>`), стабильное для конкретного события. Продюсер
(`publishBookingEvent`) MUST проставлять `event_id` при публикации. Consumer MUST использовать
`event_id` как ключ дедупликации.

#### Scenario: Публикуемое событие содержит event_id
- **WHEN** сервис публикует любое событие бронирования
- **THEN** тело события содержит непустой `event_id` в формате `evt-<uuid>`

#### Scenario: Consumer дедуплицирует по event_id из тела события
- **WHEN** нотификатор обрабатывает событие
- **THEN** он использует `event_id` из тела события как ключ проверки/фиксации в `processed_events`
